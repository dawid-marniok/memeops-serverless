Wasm a zwykły kontener

Czym jest WebAssembly, co dokładnie się zmienia, gdy pod uruchamia moduł .wasm zamiast kontenera, i kiedy to się opłaca. W skrócie: Wasm nie zastępuje poda, tylko proces w kontenerze. Wygrywa startem instancji, gęstością i rozmiarem, a nie startem poda.

W skrócie

Co to jest Wasm?

Przenośny kod bajtowy dla wirtualnego procesora. Kompilujesz Rust, Go czy C raz, a uruchamia go runtime (np. wasmtime) na x86 i ARM.

Czym różni się od kontenera?

Kontener pakuje cały system plików Linuksa i działa na jądrze hosta. Moduł Wasm to sama aplikacja, która widzi tylko to, co runtime jej przyzna.

Czy pod Wasm startuje szybciej?

Nie. W demo 12: 1,0 s vs 0,99 s. Czas startu poda to kubelet, sandbox i sieć, nie sam proces.

To gdzie jest zysk?

Start instancji w milisekundach wewnątrz działającego runtime’u, gęstość wielu aplikacji w jednym procesie, artefakty po kilka MB.

Czy przeniosę na Wasm swoją aplikację w Pythonie?

Zwykle nie wprost. Biblioteki z kodem C (Pillow, część numpy), wątki i surowe gniazda to dziś główne ograniczenia.

1Co to jest WebAssembly

WebAssembly (Wasm) to binarny format instrukcji dla wymyślonego, prostego procesora. Nie ma takiego procesora w krzemie. Program w Wasm uruchamia runtime, który tłumaczy te instrukcje na kod maszynowy prawdziwego CPU (JIT albo z góry, AOT). To ten sam pomysł co bajtkod JVM, ale z trzema różnicami, które tu są najważniejsze:

  • Wiele języków. Do Wasm kompilujesz Rust, C/C++, Go (TinyGo albo GOOS=wasip1), Zig, a z ograniczeniami też JavaScript i Pythona.
  • Domyślnie nic nie wolno. Moduł nie ma dostępu do plików, sieci ani zegara, dopóki host mu ich jawnie nie da.
  • Mały i szybki start. Moduł ma zwykle od kilkuset kB do kilku MB. Runtime tworzy jego instancję w milisekundach albo szybciej.

Skąd się wziął i co to jest WASI

Wasm powstał dla przeglądarki (standard W3C od 2019 r.), żeby szybko i bezpiecznie uruchamiać tam kod spoza JavaScriptu, np. edytory grafiki. W przeglądarce kontakt ze światem zapewnia JavaScript. Na serwerze takiego pośrednika nie ma, dlatego powstał WASI (WebAssembly System Interface): standardowy zestaw funkcji, które host udostępnia modułowi, czyli pliki, zegar, losowość, gniazda i HTTP.

  • WASI Preview 1 (wasip1) jest prosty i przypomina POSIX.
  • WASI 0.2 (Preview 2, styczeń 2024) opiera się na component model: moduły mają typowane interfejsy (WIT), np. wasi:http, i można je składać jak klocki, nawet gdy napisano je w różnych językach.
  • WASI 0.3 dodaje natywną asynchroniczność. Stan wydania sprawdź na wasi.dev.
Zdanie do zapamiętania, Solomon Hykes (twórca Dockera), 2019: „Gdyby WASM+WASI istniały w 2008 roku, nie musielibyśmy tworzyć Dockera”. Uczciwy kontekst: dodał wtedy, że Docker i Wasm będą działać obok siebie, a nie że jedno zastąpi drugie.

Analogia

Kontener to wynajęte mieszkanie z własnymi meblami (biblioteki, interpreter, /bin) w bloku, który dzieli fundamenty (jądro) z sąsiadami. Moduł Wasm to pokój w hotelu: przynosisz tylko walizkę (sam kod), a recepcja (runtime) decyduje, do których drzwi dostajesz klucz.

2Co jest w środku: warstwa po warstwie

Dolne warstwy są wspólne. Różnica zaczyna się na wysokości runtime’u kontenera: runc tworzy proces Linuksa w namespaces, a shim Spin ładuje moduł do wasmtime.

3Izolacja: dwa różne pomysły

Kontener odgradzanie procesu

Proces w kontenerze to zwykły proces Linuksa. Jądro pokazuje mu własny widok systemu (namespaces: PID, sieć, mount, user) i ogranicza zasoby (cgroups). Proces może wywołać każdy syscall, a seccomp i capabilities wycinają te niebezpieczne. Izolacja jest tak dobra, jak dobre jest jądro i konfiguracja. Stąd pomysły typu gVisor czy Kata Containers, gdy uruchamiasz cudzy kod.

Wasm brak drzwi zamiast zamków

Moduł Wasm ma pamięć liniową, czyli jedną tablicę bajtów, poza którą nie może pisać ani czytać. Nie ma instrukcji „wywołaj syscall”. Może tylko wołać funkcje, które host mu zaimportował. Jeśli host nie dał funkcji do otwierania gniazd, moduł fizycznie nie ma jak się połączyć z siecią. To jest capability-based security: domyślnie zero, uprawnienia dodajesz pojedynczo.

⚠ „Wasm jest bezpieczniejszy od kontenera” to prawda tylko z zastrzeżeniami. Runtime (wasmtime) też może mieć błędy, a w Kubernetesie moduł i tak działa w podzie z cgroupami. Dokładniej: mniejsza powierzchnia ataku i deny-by-default, czyli dodatkowa warstwa, a nie zamiennik.

4Wasm bez Kubernetesa

Wasm to format programu, a nie platforma. Moduł uruchomisz bez Kubernetesa, a nawet bez kontenerów. Kubernetes to tylko jeden ze sposobów, żeby uruchamiać go na wielu maszynach. Do nauki najlepiej zacząć lokalnie.

Spróbuj: moduł w Rust i wasmtime

# runtime i target Wasm dla Rusta
curl https://wasmtime.dev/install.sh -sSf | bash   # Linux (VM szkoleniowa)
brew install wasmtime                               # macOS
rustup target add wasm32-wasip1

# zwykły program w Rust, skompilowany do Wasm zamiast na Twój system
cargo new hello && cd hello
cargo build --release --target wasm32-wasip1
ls -lh target/wasm32-wasip1/release/hello.wasm     # mały plik, ten sam na x86 i ARM
wasmtime run target/wasm32-wasip1/release/hello.wasm

# uprawnienia: bez --dir moduł nie widzi żadnego pliku
wasmtime run app.wasm                 # odczyt pliku kończy się błędem
wasmtime run --dir=. app.wasm         # dostęp tylko do bieżącego katalogu

Spróbuj: aplikacja HTTP w Spinie

# Linux: instalator ze spinframework.dev → Install
# macOS — uwaga: samo „brew install spin” instaluje inne narzędzie o tej nazwie
brew tap spinframework/tap
brew install spinframework/tap/spin

spin new -t http-rust hello-spin && cd hello-spin

Ta sama aplikacja trafia potem do Kubernetesa: spin registry push pakuje moduł i spin.toml do obrazu OCI, a w klastrze uruchamia ją shim (demo 12) albo SpinKube.

W skrócie: Wasm to format programu, a nie platforma. Uruchamiasz go wasmtime run jak zwykłą binarkę. Kubernetes dokłada tylko to, co dokłada każdej aplikacji: harmonogram, sieć i skalowanie.

5Jak Wasm wchodzi do Kubernetesa

Kubernetes nic nie wie o Wasm. Jedyny punkt zaczepienia to RuntimeClass: pod mówi „uruchom mnie handlerem spin”, kubelet przekazuje to containerd, a containerd zamiast runc woła shim, czyli małą binarkę, która umie uruchomić moduł.

Trzy elementy, które musisz mieć

  1. Binarka shima na węźle. W demo jest w obrazie węzła kind containerd-shim-spin/kind:v0.26.0. Na prawdziwym klastrze instaluje ją runtime-class-manager ze SpinKube.
  2. Wpis w konfiguracji containerd, który łączy nazwę handlera z shimem. Bez niego dostaniesz no runtime for "spin" is configured (pułapka z próby 29.10, dlatego demo/12-wasm/kind-wasm.yaml ma containerdConfigPatches).
  3. RuntimeClass w API i runtimeClassName w podzie.
# demo/12-wasm/1-runtimeclass.yaml i 2-aplikacje.yaml (fragment)
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: wasmtime-spin-v2
handler: spin                 # nazwa runtime'u w containerd
---
spec:
  template:
    spec:
      runtimeClassName: wasmtime-spin-v2
      containers:
        - name: hello
          image: ghcr.io/spinframework/containerd-shim-spin/examples/spin-rust-hello:v0.26.0
          command: ["/"]      # tak w przykładach shima; aplikację opisuje spin.toml w obrazie

SpinKube, czyli wersja „na produkcję”

SpinKube (CNCF Sandbox od 01.2025) składa to w całość: spin-operator z zasobem SpinApp (zamiast ręcznego Deploymentu), containerd-shim-spin i runtime-class-manager, który instaluje shim na węzłach. Na AKS pule węzłów WASI wycofano 20.07.2025, więc dziś drogą na AKS jest właśnie SpinKube.

6Dlaczego pod Wasm nie wstaje szybciej

To najważniejsza część dla tego szkolenia. Od scale 0 → 1 do Ready kubelet robi wiele rzeczy, a Wasm przyspiesza tylko jedną z nich.

Skąd więc „milisekundy” w materiałach marketingowych

To dwa różne pomiary:

  • Start poda: kubelet, sandbox, sieć, probe. Około sekundy niezależnie od tego, co jest w środku.
  • Start instancji: runtime już działa, moduł jest skompilowany, trzeba tylko utworzyć nową instancję. Spin robi to przy każdym żądaniu HTTP, w czasie poniżej milisekundy do kilku ms.

W Kubernetesie cold start funkcji to cold start poda. Zysk Wasm widać dopiero wtedy, gdy pod (albo proces runtime’u) już działa i obsługuje wiele aplikacji albo wiele instancji naraz. Tak działają platformy edge i serwerowy model Spina.

⚠ „Wasm do 1000× szybciej” nie ma pierwotnego źródła. Fermyon podaje start instancji poniżej 1 ms, WasmEdge „100×”, niezależne pomiary są mieszane. Bezpieczne sformułowanie: milisekundy zamiast setek milisekund startu instancji, według danych producentów.

8Kiedy warto, a kiedy nie

Warto rozważyć

  • Wiele małych funkcji HTTP z ruchem skokowym i chęć upchnięcia ich gęsto na węźle
  • Uruchamianie kodu klientów albo wtyczek (multi-tenant), gdzie liczy się deny-by-default
  • Edge z mieszanką x86 i ARM, wolne łącze, mało miejsca na dysku
  • Nowy kod w Rust, Go albo TinyGo, bez ciężkich zależności natywnych
  • Rozszerzanie istniejącego systemu (Envoy, polityki) zamiast osobnego serwisu

Zostań przy kontenerze

  • Istniejąca aplikacja w Pythonie lub Javie z bibliotekami w C (Pillow, część numpy, sterowniki baz)
  • Potrzebne wątki, surowe gniazda, dostęp do urządzeń, GPU
  • Długo żyjąca usługa ze stanem w pamięci (Spin tworzy nową instancję na żądanie)
  • Problemem jest cold start poda: tu pomaga min-scale, nie Wasm
  • Zespół potrzebuje debuggera, strace i znanych narzędzi na produkcji

9Wasm w telco: edge, multi-tenant, 5G/6G

Przy multi-tenant i przetwarzaniu bliżej sieci Wasm jest ciekawy z innego powodu niż szybkość poda:

  • Gęstość na edge. Wiele funkcji różnych dzierżawców w jednym procesie, bez osobnego poda dla każdej.
  • Izolacja cudzego kodu bez kosztu osobnej maszyny wirtualnej.
  • Badania. OpenWhisk z Wasm i podobne prace (patrz Frameworki serverless): projekt OpenWhisk ma niską aktywność, więc to temat do eksperymentów, nie na produkcję.

Granica: funkcje near-RT z budżetem latencji w milisekundach nie mogą czekać na cold start poda, niezależnie od Wasm. Tam i tak pod musi być warm (min-scale), więc pytanie brzmi: czy zysk na starcie instancji ma znaczenie, gdy pod już działa? Więcej: Knative, HPA czy KEDA w aplikacji near-RT.

❓ Sprawdź u siebie: jaki budżet latencji ma Twoja funkcja? Czy zysk kilku ms ma znaczenie, skoro pod i tak musi być warm?

11Sprawdź się

Czym Wasm na Kubernetesie różni się od kontenera i dlaczego pod nie startuje szybciej?

Pod jest ten sam: kubelet, sandbox, sieć, cgroupy, probe'y. Zmienia się tylko to, co containerd uruchamia w środku. Zamiast runc i procesu Linuksa z własnym systemem plików shim Spin ładuje moduł .wasm do wasmtime. Moduł ma kilka MB, działa na każdym CPU i domyślnie nie ma dostępu do niczego. Start poda to głównie koszty kubeleta, więc wynik jest ten sam: 1,0 s vs 0,99 s. Wasm wygrywa startem instancji w działającym runtime, gęstością i rozmiarem.

Co jest w obrazie OCI aplikacji Spin?

Moduł .wasm i spin.toml (manifest: trasy HTTP, uprawnienia, np. allowed_outbound_hosts). Nie ma dystrybucji Linuksa, /bin ani interpretera. Obraz ma kilka MB.

Dodajesz runtimeClassName: wasmtime-spin-v2, ale pod wisi z błędem no runtime for "spin" is configured. Co brakuje?

Wpisu w konfiguracji containerd na węźle, który łączy handler spin z io.containerd.spin.v2. Sama binarka shima i RuntimeClass nie wystarczą. W demo robi to containerdConfigPatches w demo/12-wasm/kind-wasm.yaml, w SpinKube robi to runtime-class-manager.

Ktoś mówi: „przenieśmy nasz serwis w Pythonie z Pillow na Wasm, będzie 1000× szybciej”. Co odpowiesz?

Po pierwsze, Pillow ma kod natywny w C, więc nie przeniesie się wprost. Po drugie, „1000×” nie ma pierwotnego źródła, a w Kubernetesie start poda się nie zmienia (demo: 1,0 s vs 0,99 s). Jeśli problemem jest cold start, pomoże min-scale i mniejszy obraz. Wasm rozważ dla nowych, małych funkcji.

Dlaczego Spin może tworzyć nową instancję na każde żądanie, a Python nie?

Bo instancja Wasm powstaje w milisekundach albo szybciej: moduł jest już skompilowany, trzeba tylko przydzielić pamięć liniową. Start interpretera Pythona z importami trwa dziesiątki do setek ms, więc proces musi żyć długo. Skutek uboczny w Spinie: brak stanu w pamięci między żądaniami, stan trzymasz w key-value albo bazie.

Czy Wasm jest bezpieczniejszy niż kontener?

Ma mniejszą powierzchnię ataku: brak syscalli, pamięć ograniczona do jednej tablicy, uprawnienia nadawane jawnie. Ale runtime też może mieć błędy, a w Kubernetesie moduł działa i tak w podzie z cgroupami. To dodatkowa warstwa obrony, nie zamiennik izolacji.

Klient pyta o Wasm na AKS. Co mu powiesz?

Pule węzłów WASI w AKS wycofano 20.07.2025. Dziś drogą jest SpinKube: runtime-class-manager instaluje shim na węzłach, spin-operator zarządza zasobami SpinApp.

Czym WASI 0.2 różni się od Preview 1?

Preview 1 to prosty interfejs w stylu POSIX (pliki, zegar). WASI 0.2 opiera się na component model: typowane interfejsy w WIT (np. wasi:http), moduły z różnych języków da się składać ze sobą.
