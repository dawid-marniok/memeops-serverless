Handler a zwykły kontener

Czym jest handler, co robi func create i dlaczego na końcu obie drogi kończą się tym samym Knative Service.

Handler to funkcja, którą platforma wywołuje przy każdym żądaniu. Ty piszesz tylko to, co ma się stać z żądaniem. Serwer HTTP, port, health probe'y i obraz kontenera daje szablon. Analogia: handler to urządzenie podłączane do gniazdka. Gniazdko, czyli serwer, port i kontener, daje platforma. Ty decydujesz tylko, co urządzenie robi, gdy popłynie prąd, czyli gdy przyjdzie żądanie.

Zwykły kontener · main.py (skrót z szablonu firmowego)

def handle(method, path, body):
    return 200, {"hello": "MemeOps"}

class Handler(BaseHTTPRequestHandler):
    def _serve(self):
        if self.path == "/healthz":
            status, out = 200, {"ok": True}
        else:
            status, out = handle(...)
        self.send_response(status)
        self.send_header("Content-Type", ...)
        self.end_headers()
        self.wfile.write(json.dumps(out).encode())
    do_GET = do_POST = _serve

if __name__ == "__main__":
    port = int(os.environ.get("PORT", "8080"))
    ThreadingHTTPServer(("", port), Handler) \
        .serve_forever()

Wyzwalacz → platforma → handler

Handler nie decyduje, kiedy aplikacja startuje. Mówi tylko, co zrobić ze zdarzeniem.

Wyzwalacz
kiedy?

żądanie HTTP, webhook, cron, wiadomość z kolejki

→
Platforma
kto odbiera i budzi?

Knative activator (gdy 0 podów) → start poda → serwer z szablonu na porcie

→
Handler
co zrobić?

twoje handle() → odpowiedź

Przy cold starcie z LAB 2 pierwsze żądanie odebrał activator, a nie handler. Handler dostał je dopiero, gdy pod już działał. Analogia: wyzwalacz to dzwonek do drzwi, platforma to ktoś, kto słyszy dzwonek i otwiera, a handler to rozmowa z gościem w progu.

Ten sam handler, inne wejście

-t http · surowe żądanie

async def handle(self, scope, receive, send):
    path = scope["path"]   # np. /api/memes

-t cloudevents · gotowe zdarzenie

async def handle(self, scope, receive, send):
    event = scope["event"] # type="photo.uploaded"

O tym, kto i kiedy zawoła handler, decyduje konfiguracja w klastrze (Source, Broker, Trigger), a nie kod funkcji.

Kiedy co wybrać

Funkcja z func

  • chcesz szybko zacząć
  • zespół nie chce utrzymywać Dockerfile
  • funkcja jest mała i robi jedną rzecz

Zwykły kontener / szablon firmowy

  • firma ma zasady dla obrazów: baza, bez roota, skanowanie
  • zależności natywne (Pillow, biblioteki C)
  • aplikacja już działa w kontenerze
Złoty środek: func create --repository z firmowym repozytorium szablonów. Programista pisze tylko handler, a zasady firmy siedzą w szablonie.
